# Fine-tuned LLM Agent Simulation

This directory contains the implementation of fine-tuned LLM agent simulations for predicting individual evacuation decisions during the 2021 Marshall Fire.

The simulation framework integrates Meta-Llama-3.1-8B-Instruct with fold-specific LoRA adapters trained on synthetic mobility-informed agent data. It uses Mesa for agent-based simulation and vLLM for LLM inference.

The workflow evaluates held-out agents from five spatially separated test folds and supports feature ablation experiments to examine the contribution of socioeconomic and disaster-related contextual information.

## 1. Overview

The fine-tuned simulation workflow consists of the following steps:

1. Load the pretrained Llama-3.1-8B-Instruct model.
2. Load the LoRA adapter corresponding to each spatial fold.
3. Load the held-out test dataset for the same fold.
4. Construct agent-level prompts using lifestyle, neighborhood, and disaster-related information.
5. Generate evacuation decisions using the fine-tuned LLM.
6. Parse the generated responses and record individual evacuation predictions.
7. Save agent-level results and experiment summaries.

Each fold is evaluated independently using its corresponding fine-tuned adapter.

The held-out evacuation labels are not included in the LLM prompts.

## 3. Model and LoRA Adapters

The inference pipeline uses:

- **Base model:** Meta-Llama-3.1-8B-Instruct
- **Fine-tuning method:** LoRA
- **Inference engine:** vLLM
- **Agent-based modeling framework:** Mesa
- **Precision:** BF16

The base model must be downloaded separately and made available locally.

The fine-tuned adapters are generated by the LoRA training pipeline described in `code/LoRA/README.md`.

Each fold requires its corresponding adapter:

```text
code/LoRA/outputs/training/
├── fold1/
│   └── final_adapter/
├── fold2/
│   └── final_adapter/
├── fold3/
│   └── final_adapter/
├── fold4/
│   └── final_adapter/
└── fold5/
    └── final_adapter/
```

The inference pipeline loads the adapter from the same fold as the test dataset.

For example, Fold 1 inference uses `fold1_test.csv` and the adapter stored under `fold1/final_adapter/`.

The base model and trained LoRA adapters are not included in the synthetic data directory.

## 4. Input Data

The simulation uses the held-out test datasets provided in:

```text
data/synthetic/csv/
├── fold1_test.csv
├── fold2_test.csv
├── fold3_test.csv
├── fold4_test.csv
└── fold5_test.csv
```

Each CSV contains synthetic agent-level information used to construct the evacuation simulation prompts.

The required columns are:

| Column | Description |
|---|---|
| `persona_id` | Unique identifier for each synthetic agent. |
| `geoid` | Geographic identifier of the agent's residential area. |
| `tract_id` | Census tract identifier. |
| `persona_output` | Natural-language description of the agent's lifestyle and mobility patterns. |
| `distance_to_fire_km` | Distance from the agent's residential location to the fire ignition location. |
| `direction_from_fire` | Direction of the residential location relative to the fire. |
| `total_population_category` | Neighborhood population category. |
| `median_income_category` | Neighborhood income category. |
| `white_population_category` | Neighborhood racial composition category. |
| `alert_level` | Initial evacuation alert information. |

For compatibility with earlier dataset formats, the runner also supports `tract_id_x` as an alternative to `tract_id` and `output` as an alternative to `persona_output`.

If the optional `evacuated` and `evacuation_label` columns are available, their values are retained in the prediction output for subsequent evaluation. These labels are not provided to the LLM as prompt inputs.

The simulation uses CSV inputs directly. The JSONL training files are not required for this inference workflow.

## 5. Simulation Framework

The simulation framework is implemented using Mesa and integrates fine-tuned LLMs to predict individual evacuation decisions during the Marshall Fire.

Each individual is represented by an `LLMAgent`, which incorporates lifestyle, mobility, neighborhood, and disaster-related attributes.

For each individual, the simulation follows these steps:

1. Construct a prompt using the individual's contextual information.
2. Format the prompt using the model tokenizer's native chat template.
3. Generate a response using the fine-tuned LLM.
4. Extract the evacuation decision from the generated response.
5. Record the predicted decision and the complete generated response.

The simulation is configured to evaluate the initial evacuation decision using a single simulation step.

The predicted evacuation decisions are categorized as:

- `evacuate`
- `not evacuate`

The generated responses and corresponding evacuation predictions are saved for subsequent analysis.

## 6. Prompt Construction

Each agent receives a prompt consisting of a system message and a user message.

The user message contains three major components:

**Lifestyle information**

A natural-language description of the agent's mobility patterns and lifestyle characteristics.

**Neighborhood and spatial information**

Selected socioeconomic characteristics, fire distance, relative direction, and initial evacuation alert information.

**Disaster information**

A description of the 2021 Marshall Fire and the disaster conditions available in the simulation scenario.

The model is instructed to explain its reasoning before providing a final evacuation decision in one of the following formats:

- `Final answer: Evacuate`
- `Final answer: Not evacuate`

The generated reasoning and final decision are recorded in the output files.

## 7. Feature Ablation Experiments

The inference pipeline supports nine predefined feature configurations.

These configurations are specified in `inference_config.yaml`.

The six configurable contextual features are:

| Feature | Description |
|---|---|
| A1 | Distance from the fire |
| A2 | Neighborhood total population category |
| A3 | Neighborhood median household income category |
| A4 | Neighborhood white population composition |
| A5 | Direction relative to the fire |
| A6 | Initial evacuation alert |

The predefined experiments are:

| Experiment | Included Features |
|---|---|
| E1 | A1, A2, A3, A4, A5, A6 |
| E2 | A1, A3, A4, A5, A6 |
| E3 | A1, A2, A4, A5, A6 |
| E4 | A1, A2, A3, A5, A6 |
| E5 | A1, A5, A6 |
| E6 | A2, A3, A4, A5, A6 |
| E7 | A1, A2, A3, A4, A6 |
| E8 | A1, A2, A3, A4, A5 |
| E9 | A2, A3, A4 |

E1 represents the complete feature configuration.

E2–E9 systematically exclude individual features or groups of features to evaluate their contributions to simulated evacuation behavior.

Unless a specific experiment is selected, the runner executes all nine configured experiments.

## 8. Inference Configuration

The primary inference settings are specified in `inference_config.yaml`.

### Model Configuration

| Parameter | Value |
|---|---|
| Base model | Meta-Llama-3.1-8B-Instruct |
| Precision | BF16 |
| Maximum model length | 6,144 |
| GPU memory utilization | 0.90 |
| Maximum concurrent sequences | 64 |
| LoRA rank | 16 |
| LoRA enabled | Yes |

### Generation Configuration

| Parameter | Value |
|---|---|
| Maximum generated tokens | 1,024 |
| Temperature | 0.8 |
| Top-p | 0.85 |
| Top-k | 30 |
| Number of outputs per request | 1 |

The inference script uses these parameters to configure vLLM sampling.

### Simulation Configuration

| Parameter | Value |
|---|---|
| Iteration | 1 |
| Base seed | 6000 |
| Inference seed | 6001 |
| Simulation steps | 1 |
| Maximum agents | No limit by default |

The inference seed is calculated as:

```python
seed = base_seed + iteration
```

The provided Slurm script runs one iteration per fold with an inference seed of 6001.

## 9. Configuration and Paths

Before running inference, users must configure the local model path, held-out test data path, LoRA adapter directory, and output directory.

The `inference_config.yaml` file defines the default path templates:

```yaml
paths:
  model_path: "/path/to/Llama-3.1-8B-Instruct"
  data_csv_template: "/path/to/data/fold{fold}_test.csv"
  adapter_path_template: "/path/to/adapters/fold{fold}/final_adapter"
  output_dir: "./outputs/fine_tuned"
```

These are example paths and must be replaced or overridden with valid paths in the user's computing environment.

The `{fold}` placeholder is automatically replaced with the corresponding fold number.

### Environment Variables

The Slurm script uses environment variables to configure the inference workflow.

| Variable | Description |
|---|---|
| `MODEL_PATH` | Local directory containing the base model. |
| `DATA_DIR` | Directory containing fold-specific test CSV files. |
| `ADAPTER_ROOT` | Directory containing the five fold-specific LoRA adapter directories. |
| `OUTPUT_DIR` | Directory for simulation outputs. |
| `CONTAINER_IMAGE` | Container image used for execution. |
| `CONTAINER_RUNTIME` | Container runtime, defaulting to Singularity. |
| `OVERLAY_FILE` | Optional container overlay. |
| `CONTAINER_ENV_SCRIPT` | Optional environment initialization script. |
| `CACHE_ROOT` | Cache directory for model and inference dependencies. |

For Slurm execution, `MODEL_PATH`, `DATA_DIR`, `ADAPTER_ROOT`, and `CONTAINER_IMAGE` must be configured before submission.

The Slurm script passes the fold-specific data and adapter locations to the Python inference runner.

Users do not need to modify the Python scripts to change these paths.

## 10. Execution

### 10.1 Environment Setup

Refer to the repository-level `README.md`, `requirements.txt`, and `environment.yml` for installation instructions.

The fine-tuned simulation workflow requires a compatible CUDA-enabled GPU environment, the base LLM, and the trained LoRA adapters from all five folds.

For HPC execution, a compatible container runtime and container image are also required.

### 10.2 Configure Paths

From the repository root, navigate to the fine-tuned simulation directory:

```bash
cd code/simulation/finetuned
```

Configure the model, dataset, adapter, output, and container paths:

```bash
export MODEL_PATH="/path/to/llama-3.1-8b-instruct"
export DATA_DIR="$(realpath ../../../data/synthetic/csv)"
export ADAPTER_ROOT="$(realpath ../../LoRA/outputs/training)"
export OUTPUT_DIR="$(pwd)/outputs"
export CONTAINER_IMAGE="/path/to/container.sif"
```

Replace the example model and container paths with the corresponding locations in your computing environment.

The adapter root should contain the five fold-specific subdirectories generated by the LoRA training pipeline.

If the adapters are stored elsewhere, update `ADAPTER_ROOT` accordingly.

The following optional variables can also be configured when needed:

```bash
export CONTAINER_RUNTIME="singularity"
export OVERLAY_FILE="/path/to/overlay.ext3"
export CONTAINER_ENV_SCRIPT="/path/to/env.sh"
```

The optional overlay and environment initialization script depend on the target HPC environment.

### 10.3 Full Five-Fold Inference

The complete fine-tuned simulation workflow requires inference on all five held-out spatial folds.

The provided `run_finetuned.slurm` script uses a Slurm job array:

```bash
#SBATCH --array=1-5%5
```

Each task uses its corresponding test dataset and LoRA adapter.

| Slurm Task | Input Dataset | LoRA Adapter |
|---|---|---|
| 1 | `fold1_test.csv` | `fold1/final_adapter/` |
| 2 | `fold2_test.csv` | `fold2/final_adapter/` |
| 3 | `fold3_test.csv` | `fold3/final_adapter/` |
| 4 | `fold4_test.csv` | `fold4/final_adapter/` |
| 5 | `fold5_test.csv` | `fold5/final_adapter/` |

Submit the five-fold simulation jobs:

```bash
mkdir -p slurm_logs
sbatch run_finetuned.slurm
```

Each fold runs independently using one GPU. Up to five tasks may run simultaneously, subject to available cluster resources.

By default, each task runs one iteration of all nine configured feature experiments for its corresponding held-out fold.

### 10.4 Simulation Completion

Job execution can be monitored using:

```bash
squeue -u "$USER"
```

The Slurm output and error logs are saved under `slurm_logs/`.

After all five jobs finish successfully, the results should be available in the configured output directory.

## 11. Output Structure

The inference results are saved separately for each fold, iteration, and experiment.

```text
outputs/
├── fold1/
│   └── iteration_1/
│       ├── E1/
│       │   ├── agent_predictions.csv
│       │   └── summary.csv
│       ├── E2/
│       ├── ...
│       └── E9/
├── fold2/
├── fold3/
├── fold4/
└── fold5/
```

### Agent-level Predictions

Each `agent_predictions.csv` contains the individual simulation results.

The output fields include:

| Column | Description |
|---|---|
| `iteration` | Simulation iteration. |
| `experiment` | Feature configuration identifier. |
| `agent_id` | Synthetic agent identifier. |
| `geoid` | Geographic identifier. |
| `tract_id` | Census tract identifier. |
| `fire_distance_km` | Distance to fire. |
| `direction_from_fire` | Direction relative to fire. |
| `alert_level` | Initial evacuation alert information. |
| `predicted_decision` | Parsed evacuation decision. |
| `predicted_evacuated` | Boolean evacuation prediction, or missing for unparsed responses. |
| `ground_truth_evacuated` | Optional held-out reference outcome. |
| `ground_truth_label` | Optional held-out reference label. |
| `inference_seconds` | LLM inference duration for the agent. |
| `generated_response` | Full generated LLM response, including any reasoning text. |

### Experiment Summary

Each `summary.csv` contains the corresponding experiment-level statistics.

These include the number of agents, evacuated predictions, non-evacuated predictions, unparsed responses, predicted evacuation rate, and inference seed.

The predicted evacuation rate is calculated among responses successfully parsed as either evacuate or not evacuate.

## 12. Reproducibility Notes

The provided implementation documents the model inference settings, prompt construction, feature ablation configurations, fold-specific adapter loading, and simulation output formats.

The synthetic datasets included in this repository are intended to demonstrate the computational workflow.

Results obtained using these datasets may differ from those reported in the associated manuscript because the original experiments were conducted using the underlying research datasets and corresponding trained model adapters.

Reproducing the original numerical results requires the relevant research datasets, base-model checkpoint, fine-tuned adapters, and compatible computational environment.
